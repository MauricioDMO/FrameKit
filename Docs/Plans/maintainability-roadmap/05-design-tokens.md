# Phase 5 - Published Semantic Design Tokens

## Status

- **Status:** Proposed; not yet implemented.
- **PR boundary:** One behavior-preserving published-CSS and product-shell
  class migration, separate from Phase 4's responsibility split.
- **Public API:** The existing `.`, `./editor`, `./studio`, `./studio/root`,
  `./dev`, and `./styles.css` exports remain unchanged. This phase intentionally
  adds only the 15 consumer-facing `--fk-*` theme roles listed below as supported
  API inside the existing stylesheet export. Private `--_fk-*` palette and
  component/state aliases, Tailwind theme registrations, and generated utility
  classes are implementation details, not compatibility promises. No new import
  path or JavaScript/TypeScript export is added.

## Depends on

- **Sequencing dependency:** Phase 4 must be merged first, as promised by the
  ordered roadmap.
- **Shared-check dependency:** Phase 1 must also be merged before running the
  full gate below because it supplies the repository `format:check` script. The
  current pre-roadmap checkout does not define that script.
- **Code dependency:** None on Phase 4's runtime behavior; token consumers must
  follow the shell ownership present after Phase 4.
- `DESIGN.md` as palette evidence and the current product-shell classes.
- `packages/framekit/src/styles.css` as the only source of published tokens.

## Goal

Introduce a small set of stable light/dark theme roles that consumers can use to
customize FrameKit's reusable Studio/editor chrome. Replace repeated
product-shell palette literals with semantic utilities while preserving the
current visual values, interaction behavior, and
`@mauriciodmo/framekit/styles.css` export. Palette constants and granular
component/state roles remain private implementation details. A value documented
in `DESIGN.md` but used only by authored artwork is not a reason to add any
token.

This is a maintainability change, not a redesign. `DESIGN.md` records the
forest, mint, sage, ivory, and ink evidence; it is not a second token source.
Never edit `packages/framekit/dist/styles.css` by hand: it is generated by the
package build from `src/styles.css`.

## Current baseline

- `packages/framekit/src/styles.css` imports Tailwind v4, defines the custom
  `dark` variant, scans `./editor` and `./studio`, and owns the published CSS
  consumed through the unchanged `./styles.css` package export.
- `DESIGN.md` identifies `forest-950` through `forest-700`, mint, sage,
  ivory, and ink values and directs dark Studio surfaces to stay in the
  forest family.
- Product-shell JSX currently repeats palette literals across the Studio shell,
  editor header/controls, fields, preview, navigation, brand catalog, root
  body, loading state, error states, and select styling. Many dark variants
  are explicit classes rather than shared variables.
- `apps/studio/src/app/globals.css` defines the existing custom `dark` variant
  and imports Tailwind. Its layout imports the published FrameKit stylesheet.
  The canonical template's
  `src/app/globals.css` imports Tailwind and `@mauriciodmo/framekit/styles.css`.
  Neither app should become a second token source.
- Template and brand render output can contain author-selected colors and
  artwork values. Those are data/component inputs, not Studio chrome.

### Tailwind v4 consumption

This applies Tailwind v4 facilities already used by the package—`@import
"tailwindcss"`, `@custom-variant`, `@source`, and the package's `build:css`
script—rather than introducing a Tailwind migration or upgrade.

After the palette constants and public/private aliases, register every role
needed by the mapped source files in `@theme inline` using the exact
`--color-fk-<role>` name that produces the corresponding utility. Public roles
reference `--fk-*`; implementation-only roles reference `--_fk-*`. Never
register the private palette directly. The registration must include the
sidebar, text, border, action, focus, preview, loading, picker, overlay, and
toggle roles, not only this abbreviated example:

```css
@theme inline {
  --color-fk-app-canvas: var(--fk-app-canvas);
  --color-fk-sidebar-surface: var(--fk-sidebar-surface);
  --color-fk-sidebar-active: var(--fk-sidebar-active);
  --color-fk-panel-surface: var(--fk-panel-surface);
  --color-fk-control-surface: var(--fk-control-surface);
  --color-fk-text-primary: var(--fk-text-primary);
  --color-fk-text-secondary: var(--fk-text-secondary);
  --color-fk-border-subtle: var(--fk-border-subtle);
  --color-fk-action-primary: var(--fk-action-primary);
  --color-fk-focus-control: var(--fk-focus-control);
  --color-fk-preview-canvas: var(--fk-preview-canvas);
  --color-fk-sidebar-guide: var(--_fk-sidebar-guide);
  --color-fk-sidebar-settings-surface: var(--_fk-sidebar-settings-surface);
  --color-fk-button-surface: var(--_fk-button-surface);
  --color-fk-overlay-on-dark: var(--_fk-overlay-on-dark);
  --shadow-fk-panel: var(--_fk-shadow-panel);
}
```

Tailwind v4's `@theme inline` is the appropriate form when a generated theme
variable references another CSS variable: it emits utilities that resolve the
current `:root`/`.dark` alias at runtime. Register the private shadow aliases as
`--shadow-fk-panel`, `--shadow-fk-preview`, `--shadow-fk-brand-preview`,
`--shadow-fk-empty`, `--shadow-fk-modal`, and `--shadow-fk-picker`. Every
`--color-fk-*`/`--shadow-fk-*` registration and generated class is internal
implementation, not published utility API. Consumers may customize only the 15
documented public `--fk-*` variables. Do not add a new stylesheet export or
require consumers to import a second token file. Both the first-party layout
and canonical template already import the published stylesheet path.

### Explicit color boundaries

- **Shell chrome to tokenize:** app canvas, root/body text, sidebar surface and
  links, route tabs, settings, editor/brand headers, panels, native controls,
  buttons, labels, metadata, borders, focus rings, preview canvases, loading
  placeholders, empty/not-found states, and repeated shadows.
- **Transparent overlays:** preserve each alpha exactly. Map `white/8` to
  `--_fk-sidebar-hover`. Map overlay `white/10` to `--_fk-overlay-on-dark`, and
  dark border `white/10` to the corresponding `--fk-border-subtle`,
  `--_fk-border-preview`, or `--_fk-border-strong` role. Map dark
  control/button `white/15` to `--_fk-border-control`/`--_fk-border-button`;
  sidebar control `white/15` and `white/20` to
  `--_fk-sidebar-control-hover` and `--_fk-sidebar-control-border`;
  picker-specific `white/15` and `white/20` to
  `--_fk-select-sidebar-hover` and `--_fk-select-sidebar-border`; and the dark
  toggle's `white/20` to `--_fk-toggle-track`. Map `black/5`, `black/8`, and
  `black/10` to `--_fk-border-preview`, `--fk-border-subtle`, and
  `--_fk-border-strong`. Use `--_fk-overlay-on-light` for the modal forest
  overlay, `--_fk-sidebar-guide` for `sage-300/25`, and the private shadow roles
  for alpha shadows. Do not turn any of them into opaque palette swatches or
  public customization points.
- **User-authored template/brand artwork:** the children rendered by
  `definition.render(...)` and `<Preview />`, including their CSS and data,
  are not Studio chrome. Do not replace their colors with `fk` tokens.
- **User-selectable values:** color-field values, field defaults, uploaded
  artwork, and any user-provided color passed into a template remain literal
  data. The `#000000` color-picker fallback and test fixture values such as
  `#123456` are behavior/test data, not published palette entries.
- **Genuinely unique visual effects:** the preview/loading dot texture's
  radial-gradient stop (`#4f5e56`) may remain a literal gradient stop because
  it is decorative texture rather than a surface or text color. The select
  arrow SVG encoded strokes may likewise remain literal implementation detail
  after being checked against the palette. Document both exceptions in the
  before/after inventory rather than silently counting them as missed tokens.
- **Shadows:** explicit repeated `rgba`/`rgb` shadows are shell effects with
  semantic roles and should use the shadow aliases above; do not remove
  elevation or flatten the design. Native `shadow-sm`, `shadow-inner`, and
  similar utilities can remain when no palette literal is embedded.

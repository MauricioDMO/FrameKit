# Step 0.6 - Minimal Consumer Integration

- **Status:** Implemented and verified on 2026-09-10.

## Goal

Reduce maintained starter files and keep FrameKit integration behavior inside the
package. Preserve the existing URLs, template contract, private-render protocol,
and ordinary consumer-owned Next.js application.

The post-Step-6 starter target has five maintained files under `src/app`. The
pre-migration baseline was seven maintained files (the previous full-feature plan
described eight), while the verified current pre-Step-6 result is four maintained
`src/app` files. Generated registry bindings are disposable output and are not
copied in the creator template. This is a maintained-source count, not a promise
that codegen produces fewer files on disk.

## Depends on

- [Step 0.5](./README.md#step-05---package-clientserver-boundaries) package client
  lifecycle, server page helper, and passing package-boundary checks.
- Existing `FrameKitStudio`, `FrameKitStudioRoot`, registry generation, and CLI.
- [Step 5](./05-private-next-render-route.md) private route and Map handoff.

## Deliverables

- `withFrameKit(config?: NextConfig): NextConfig` in a new, configuration-only
  `@mauriciodmo/framekit/next` facade.
- `createStudioPage(StudioClient)` in the existing
  `@mauriciodmo/framekit/studio/root` server facade.
- Generated `studio-client.tsx` and `render-client.tsx` registry bindings.
- One `src/app/[section]/[[...slug]]/page.tsx` for editor and brand URLs.
- Removal of the starter's home page and hand-maintained render-client binding.
- Equivalent first-party Studio integration and migration instructions.

## 1. Next configuration boundary

The local `next.config.ts` becomes:

```typescript
import { withFrameKit } from '@mauriciodmo/framekit/next'

export default withFrameKit()
```

The helper owns the requirements of the standard FrameKit application:

- `distDir: '.framekit/next'`;
- `output: 'standalone'`;
- an exact, temporary `307` redirect from `/` to `/editor`.

Contract:

- Accept an ordinary `NextConfig` object; do not introduce a separate FrameKit
  configuration file or a plugin registry.
- Preserve project settings such as Studio's `turbopack.root`, headers, and
  rewrites. Do not mutate the input object.
- Compose an existing asynchronous `redirects()` callback, retaining its rules
  and order after the reserved `/` redirect. Deduplicate an existing exact `/`
  rule only if it matches the FrameKit redirect; reject a conflicting rule.
- Reject explicit conflicting `distDir` or `output` values with a clear build
  configuration error. The production CLI currently depends on these paths.
- Keep the entry importable during Next configuration evaluation: reference
  `NextConfig` through an erased type import and do not import `next/headers`,
  `next/navigation`, Studio components, codegen, `./dev`, or `./server` at runtime.
- Do not read image API secrets or start generation/browser work on import.
- Preserve existing manual Next configuration as a supported integration path
  for applications that own their home page or use the existing explicit routes.

Add the `next` tsdown entry, package export, declaration fixture, and packed
Node import check. This is the only additional public subpath in this revision;
it does not relocate the existing `createRenderPage` export.

## 2. One Studio route adapter

Replace the two editor/brand route files with:

```tsx
// src/app/[section]/[[...slug]]/page.tsx
import { createStudioPage } from '@mauriciodmo/framekit/studio/root'
import { StudioClient } from '@framekit/generated/studio-client'

export default createStudioPage(StudioClient)
```

`createStudioPage` accepts a no-required-props client component. Its returned
server page awaits `params: Promise<{ section: string, slug?: string[] }>` and
calls `notFound()` unless `section` is exactly `editor` or `brand`. It then
renders the client component without passing registry loaders through props.

The dynamic section preserves the existing `slug` parameter semantics:
`/editor/social/post` still provides `slug: ['social', 'post']`. The current
`FrameKitStudio` can continue using `useParams()` and `usePathname()`; a second
navigation parser, routing context, or editor/brand factory is unnecessary.

The private `/framekit/render/[id]` page and `/api/v1/images` handler remain
explicit static-prefix routes. Verify their precedence and the rejection of
unknown `/framekit/*`, `/api/*`, and arbitrary sections in a real Next build.
Preserve `/framekit/assets` interception in the development server.

Remove `src/app/page.tsx` only when the `withFrameKit` redirect is wired and
verified. Keep `/editor`, `/brand`, and their nested URLs unchanged.

## 3. Generate client registry bindings

Extend the existing codegen flow, keeping these as separate client modules:

```tsx
// src/generated/framekit/studio-client.tsx — generated, never hand-edited
'use client'

import { FrameKitStudio } from '@mauriciodmo/framekit/studio'
import { templates } from './templates'
import { brands } from './brands'

export function StudioClient () {
  return <FrameKitStudio templates={templates} brands={brands} />
}
```

```tsx
// src/generated/framekit/render-client.tsx — generated, never hand-edited
'use client'

import { createRenderClient } from '@mauriciodmo/framekit/client'
import { templates } from './templates'

export const RenderClient = createRenderClient(templates)
```

The private `page.tsx` imports `RenderClient` from
`@framekit/generated/render-client`. Remove the sibling hand-maintained
`render-client.tsx` from the canonical template and Studio after updating imports.

Rules:

- Keep `templates.ts` and `brands.ts` neutral registry modules. Do not mark them
  `'use client'`; Step 6 must load template definitions on the server.
- Do not combine both bindings into one barrel that makes the private renderer
  depend on the Studio shell/catalog graph.
- Use only supported FrameKit imports and consumer-local generated imports.
- Generate the bindings alongside the existing registries via
  `writeTemplateModule`, with write-if-changed behavior and a generated-file header.
- `framekit generate`, `check`, `dev`, and `build` must recreate missing bindings
  before consuming them. The creator already generates after installation; the
  skip-install path must work after install followed by a normal FrameKit command.
- Binding generation may replace only owned files under `src/generated/framekit/`;
  existing generated-asset synchronization keeps its current output locations.
  Neither flow may write or delete routes, configuration, or user-authored files.
- Keep the existing generated alias and source-template discovery. Do not add a
  second registry, virtual application, custom router, or `.framekit/app` host.

## 4. Final maintained starter shape

After Step 6, `packages/create-framekit/template/src/app/` contains exactly:

```text
layout.tsx
globals.css
[section]/[[...slug]]/page.tsx
framekit/render/[id]/page.tsx
api/v1/images/route.ts
```

| Previous full-feature source | Planned result |
|---|---|
| `page.tsx` | Removed; redirect in `withFrameKit` |
| `editor/[[...slug]]/page.tsx` + `brand/[[...slug]]/page.tsx` | One `[section]/[[...slug]]/page.tsx` |
| `framekit/render/[id]/render-client.tsx` | Removed from template; generated binding |
| `layout.tsx`, `globals.css`, private page, public handler | Retained as thin application integration |

Before Step 6 adds the API route, the target is four maintained `src/app` files.
Keep the small local layout and CSS: they own metadata, branding, fonts, and
project styling. Keep Next/PostCSS/TypeScript configuration, package metadata,
and user templates/assets. Do not remove Tailwind compilation required by
consumer-authored templates to meet an arbitrary total-file target.

Step 7 adds deployment files outside `src/app`; they do not change this metric.
The generated bindings are absent from the creator tarball and recreated in
each consumer. Reusable generator code belongs to `packages/framekit/src/tooling`,
not `packages/create-framekit/src`.

## Implementation order

1. Add the configuration facade and server Studio-page helper with focused checks.
2. Extend registry generation with the two client bindings and regenerate Studio.
3. Replace the canonical/Studio route adapters and enable the root redirect.
4. Achieve a net reduction of three maintained files per application: two pages
   become one, and the home page and render-client binding are removed.
5. Update creator-copy, generation, route integration, public-type, and tarball
   checks; document the exact maintained-source count.
6. Verify both application builds and the production private Map handoff before
   implementing Step 6.

## Verification and exit gate

- Config composition retains Studio overrides and custom redirect behavior;
  reserved-setting conflicts fail clearly and the input object is unchanged.
- Packed `./next` imports in ordinary Node without a Next request context or
  browser startup; all new public declarations resolve.
- Clean generation recreates both bindings; a second generation is stable;
  user-authored files remain untouched; empty brand catalogs still work.
- Client bindings retain directives; the private renderer has no Studio-shell
  dependency; the server can still import/load the neutral template registry.
- Real Next HTTP checks cover `/` -> `307 /editor`, `/editor`, `/brand`, nested
  slugs, invalid sections -> `404`, explicit private/API route precedence, and
  the existing development asset endpoint. Before Step 6 exists, use a test-only
  API route fixture for precedence and Map-handoff checks, never a shipped stub.
- Existing explicit editor/brand pages and hand-written render-client bindings
  remain compatible for projects that have not migrated.
- Creator skip-install and install-and-generate flows both reach a working app.
- Starter file inventory is four `src/app` files at this gate, five after Step 6;
  obsolete files and generated bindings are not copied in the creator template.
- Package/Studio/creator tests, lint, typecheck, build, packed consumer smoke, and
  production shared-Map checks pass. Do not mark this step complete on file-count
  reduction alone.

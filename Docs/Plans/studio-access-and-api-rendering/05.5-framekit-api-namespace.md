# Phase 5.5 - FrameKit API Namespace

- **Status:** Implemented; focused package, creator, and Studio adapter checks are
  passing on 2026-09-15.

## Goal

Establish the unversioned FrameKit API namespace at `/api/framekit`, move image
rendering to `/api/framekit/images/render`, and serve access and image actions
through one application catch-all route.

The API is intentionally not versioned. Its contract is coupled to the installed
`@mauriciodmo/framekit` version, so a future breaking API change will be shipped
as part of a FrameKit version rather than selected through a URL prefix.

## Depends on

- Phase 3's exact access HTTP handler and same-origin protection.
- Phase 4's token and authorization routes.
- Phase 5's Studio access UI.
- The current `createStudioImageHandler()` and private Chromium render
  pipeline.

## Scope

This phase changes HTTP placement and dispatch only. It does not change image
authentication, the image request body, render settings, data resolution,
Chromium rendering, or Studio export behavior. The image action continues to use
the authenticated `createStudioImageHandler()` implemented in the current
source. The earlier API-key-only image-handler design is historical and removed;
`FRAMEKIT_API_KEY` is not a current consumer configuration variable.

## Current application environment

The current FrameKit application contract has seven environment variables:

- `FRAMEKIT_ADMIN_USERNAME` is consumed by `bootstrapUsers()` during login's
  first-empty-database bootstrap. It defaults to `admin` and, only then, must be
  3-64 ASCII letters, numbers, `.`, `_`, or `-`. The accepted username is
  persisted in SQLite; later environment changes do not rename the user.
- `FRAMEKIT_ADMIN_PASSWORD` is consumed by `bootstrapUsers()` during that same
  first-empty-database bootstrap. It has no default, is required only when the
  database has no users, and must be 12-256 UTF-8 bytes. Only its scrypt hash is
  persisted; the password value is not stored. After a user exists, bootstrap
  returns before reading or validating this variable.
- `FRAMEKIT_DATABASE_PATH` is consumed by `getDatabase()`. It defaults to
  `.framekit-data/framekit.sqlite`; `:memory:` is also supported for a
  process-local database. File paths are resolved from the process working
  directory, their parent directory is created, and an unopenable database
  fails initialization rather than falling back. One connection is reused per
  resolved path for the process. The SQLite file, WAL/SHM companions, users,
  password hashes, sessions, API-token hashes/metadata, and schema state are
  server-side data that must be protected and persisted together.
- `FRAMEKIT_INTERNAL_ORIGIN` is consumed by `parseImageRenderConfig()` for
  image rendering. It is required and has no default; it must be an exact HTTP
  loopback origin using `localhost`, `127.0.0.1`, or `[::1]`, with no
  credentials, query, fragment, or non-root path. Invalid or missing values
  fail closed before rendering.
- `FRAMEKIT_ALLOWED_IMAGE_HOSTS` is consumed by the render-input preparation
  path. It defaults to an empty allowlist, so no external HTTPS image host is
  accepted. Otherwise it is a comma-separated list of normalized DNS
  hostnames; empty entries are ignored, IP literals and invalid hostnames are
  rejected, and duplicate hostnames collapse to one entry.
- `FRAMEKIT_MAX_CONCURRENT_RENDERS` is consumed by the render concurrency
  limiter. It defaults to `2` and accepts only decimal integers from `1` to
  `32`; invalid values fail configuration.
- `FRAMEKIT_RENDER_TIMEOUT_MS` is consumed by the image request deadline and
  browser render timeouts. It defaults to `30000` and accepts only decimal
  integers from `1` to `120000`; invalid values fail configuration.

The administrator variables are first-boot inputs, not account
synchronization settings. The database path controls persistence for access
state; the render settings are read when an image request is handled and are
not persisted in SQLite. `FRAMEKIT_PUBLIC_ORIGIN` is unsupported: current
production code does not read it, and this plan does not define a replacement
setting.

## Canonical API contract

All current FrameKit API actions live below `/api/framekit`:

```text
POST   /api/framekit/images/render

POST   /api/framekit/login
POST   /api/framekit/logout

GET    /api/framekit/account
PATCH  /api/framekit/account
POST   /api/framekit/account/password

GET    /api/framekit/tokens
POST   /api/framekit/tokens
DELETE /api/framekit/tokens/:id

GET    /api/framekit/users
POST   /api/framekit/users
PATCH  /api/framekit/users/:id
DELETE /api/framekit/users/:id
POST   /api/framekit/users/:id/password
GET    /api/framekit/users/:id/tokens
```

`/api/framekit/images` is a resource namespace, not an endpoint. Future image
actions may be added below it without creating a new top-level API prefix. This
phase adds no unrequested image actions.

The previous endpoint is removed permanently:

```text
POST /api/v1/images -> 404
```

Do not add an alias, redirect, compatibility route, or version negotiation. The
endpoint has not shipped, so there is no external compatibility contract to
preserve.

## Unified application adapter

Add one public package factory that composes the existing access and image
handlers:

```ts
createFrameKitApiHandler(templates)
```

The factory owns exact path and method dispatch. It delegates access paths to
`createStudioAccessHandler()` and `POST /api/framekit/images/render` to
`createStudioImageHandler(templates)`.

The dispatcher must preserve each delegated handler's security boundary:

- access mutations continue to require a same-origin `Origin` header and use
  session authentication;
- image requests authenticate with a database API token in a strict Bearer
  header, or with a valid same-origin session cookie when no Authorization
  header is present;
- token-authenticated image requests do not require an `Origin` header, while
  session-authenticated image requests do;
- an invalid Authorization header does not fall back to an ambient session;
- image rendering remains separate from access route functions; its
  authentication uses the access database for session/API-token validation;
- the private `/framekit/render/[id]` route remains independent and token-only.

Unknown paths return `404`. A known path with an unsupported method returns
`405` with its allowed methods. In particular, the catch-all must not pass a
`GET /api/framekit/images/render` request into the image body parser.

Do not create either of these route files:

```text
src/app/api/framekit/images/route.ts
src/app/api/v1/images/route.ts
```

The application adapter remains:

```text
src/app/api/framekit/[...action]/route.ts
```

It imports the generated `templates` registry, creates the unified handler, and
exports the supported `GET`, `POST`, `PATCH`, and `DELETE` bindings. It contains
no access, authentication, database, or rendering logic.

## Public package boundaries

Keep these existing factories and contracts intact:

```ts
createStudioAccessHandler()
createStudioImageHandler(templates)
```

Export `createFrameKitApiHandler()` from `@mauriciodmo/framekit/server`. The
new factory is the application integration point; the lower-level factories
remain independently testable and must not be duplicated inside an App Router
file.

The current source does not export `createImageHandler()`,
`parseImageApiConfig()`, or `authenticateBearer()`, and it has no
`FRAMEKIT_API_KEY` consumer. Those names belong only to the historical,
removed API-key design and are not part of this contract.

Do not add a client-capable import of Node.js, SQLite, or Playwright. Do not
move the private-render route or development asset interception into the API
dispatcher.

## Expected source and adapters

```text
packages/framekit/src/server/
packages/framekit/src/server.ts
packages/framekit/src/server/access/http/
packages/framekit/src/server/image-handler/
packages/create-framekit/template/src/app/api/framekit/[...action]/route.ts
apps/studio/src/app/api/framekit/[...action]/route.ts
```

Remove the maintained adapters at:

```text
packages/create-framekit/template/src/app/api/v1/images/route.ts
apps/studio/src/app/api/v1/images/route.ts
```

The generated consumer and first-party Studio must have the same route shape.

## Focused tests

- the unified factory dispatches every existing access route unchanged;
- `POST /api/framekit/images/render` reaches the Studio image handler;
- a valid database API token and a valid same-origin session succeed through the
  new path;
- token-authenticated image requests do not require a same-origin `Origin`
  header, while session-authenticated requests do;
- invalid Bearer authentication does not fall back to a session;
- unsupported methods return `405` with `Allow: POST` before body parsing;
- unknown `/api/framekit/images/*` actions return `404`;
- `/api/v1/images` has no maintained route and returns `404` through Next.js;
- access mutations still reject missing, malformed, and cross-origin `Origin`;
- both application adapters export the same catch-all method bindings;
- neither application contains `api/v1/images/route.ts` or
  `api/framekit/images/route.ts`;
- the private render route and `/framekit/assets` behavior are unchanged;
- the six maintained generated-consumer app files are asserted by creator and
  tarball tests.

## Exit gate

Phase 5.5 is complete when the generated consumer and first-party Studio expose
one `/api/framekit/[...action]` adapter, all current access routes remain
functional, image rendering is available only at
`POST /api/framekit/images/render`, `/api/v1/images` returns `404`, and the
Studio image handler passes its session/API-token authentication tests. The
historical API-key-only handler is not part of this gate.
